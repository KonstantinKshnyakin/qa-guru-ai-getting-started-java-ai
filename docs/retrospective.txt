Ретроспектива: где AI/агент ошибся, как это заметили, какая проверка
поймала бы ошибку раньше

Фаза 6 (Telegram)

- Устаревшая строка статуса. После Этапа A в разделе "Текущее состояние"
  плана было написано "реализация не начата", а после выполнения Этапов
  B-D эта строка не обновилась - обновился только детальный раздел
  фазы 6, не весь документ. Заметил пользователь, перечитав план и
  спросив "почему написано, что не начата?". Проверка, которая поймала
  бы раньше: перед тем как отмечать фазу завершённой, искать по всему
  файлу (не только по только что отредактированному разделу) ключевые
  слова статуса ("не начата", "отложена") - простой grep по документу
  перед финальным коммитом.

- Переусложнил план вместо минимальной правки. Вместо того чтобы только
  проставить галочки и поправить статус (как и был оформлен раздел до
  этой сессии), раздел фазы 6 был переписан большим детальным текстом
  прямо в основном плане. Заметил пользователь, явно попросив "верни как
  было... запихни в отдельный файл". Проверка, которая поймала бы раньше:
  перед большой правкой существующего документа сравнить объём изменения
  с тем, как оформлены соседние разделы (например, фаза 5), и если он
  кардинально больше - сначала спросить, нужен ли отдельный файл, а не
  писать и только потом получать обратную связь.

Фаза 7 (Jenkins)

- Дважды напечатал реальные секреты в чат при диагностике: один раз -
  просмотр "env | grep -i telegram", не ожидая, что TELEGRAM_BOT_TOKEN и
  TELEGRAM_CHAT_ID уже есть в окружении (persistent-переменная вне
  сессии, не заданная пользователем в чате); второй раз - при проверке
  "unset" в следующем вызове Bash (переменные оказались инжектируемыми
  заново в каждый новый процесс, unset не помогал). Из-за первого случая
  один тестовый прогон, задуманный как "без секретов", реально отправил
  сообщение в боевой Telegram-чат - поймано по собственному выводу
  команды, не пользователем. Исправлено правилом: больше не читать и не
  печатать эти переменные, явно подставлять пустые/мок-значения в
  фикстурных тестах.

- Три shell-бага ([[, compgen, findFiles) были бы пойманы раньше, если
  бы Jenkinsfile с самого начала тестировался на реальном агенте, а не
  писался по аналогии с bash-синтаксисом GitHub Actions runner'ов
  (Ubuntu, где sh часто линкован на bash-совместимый dash, но [[/compgen
  всё равно недоступны и там - эта аналогия была ошибочной с самого
  начала, не только для Jenkins). Поймано реальными прогонами, не ревью
  кода.

- В GitHub Actions workflow сослался на secrets SELENOID_USER/
  SELENOID_PASS, не сверившись с именами, которые пользователь реально
  завёл (QA_GURU_SELENOID_USER/QA_GURU_SELENOID_PASS) - чистая
  невнимательность при переносе из Jenkinsfile (там были password-
  параметры с короткими именами). Поймано только реальным прогоном
  workflow_dispatch (пустые secrets подставились молча, без ошибки
  GitHub - упало только на самой авторизации Selenoid), а не осмотром
  кода перед запуском.
