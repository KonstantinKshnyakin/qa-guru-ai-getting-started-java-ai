## Общие правила работы с агентом

Курс про качественную инженерную работу с AI, а не про скорость.

- Работайте фазами. Перед каждой фазой агент объясняет изменения
  и ждёт вашего подтверждения; после — показывает файлы, команды
  и фактические результаты.
- Требуйте у агента реальную проверку: «написал конфиг» ≠
  «проверил работу». HTTP 200 и зелёный YAML ничего не доказывают
  без фактического результата.
- Проверяйте версии и команды по документации и `--help`,
  а не по памяти модели. AI уверенно ошибается в именах
  артефактов и флагах.
- После каждой завершённой и проверенной фазы — отдельный
  логичный коммит. Храните план и статусы в `docs/plans/`,
  правила агента — в `AGENTS.md`.
- Запреты: секреты в коде, коммиты отчётов/результатов,
  `latest`-версии, ретраи и `continue-on-error` для маскировки
  падений, push без разрешения.

## Вариант A — фазы

Каждая фаза: изучение → согласование → реализация → проверка →
коммит. Не переходите дальше, пока критерии не выполнены.

### Фаза 0 — Baseline

Цель: понять, что у вас есть, и зафиксировать точку отсчёта.

- Прочитайте `build.gradle`, тесты, `.gitignore`, git-историю.
- Определите фактические версии Java/Gradle/зависимостей —
  не из предположений, а из файлов и `dependencies`-отчёта.
- Запустите исходный тест без изменений. Если упал — найдите
  причину до дальнейшей работы.
- Зафиксируйте результат в плане: команда, вывод, ограничения
  (внешний github.com нестабилен, возможен HTTP 429).

Критерий: есть задокументированный baseline с реальным
результатом запуска.

### Фаза 1 — TestBase и воспроизводимость

Цель: одинаковый запуск на любой машине.

- Добавьте Gradle Wrapper штатной командой `gradle wrapper`
  с проверкой официального SHA-256 дистрибутива.
- Зафиксируйте Java через toolchain.
- `TestBase`: настройка Selenide в `@BeforeEach`,
  `closeWebDriver()` в `@AfterEach`.
- Параметры `baseUrl`, `browser`, `browserSize`, `headless` —
  через `-D` с явной передачей из Gradle в JVM тестов.
  Не прокидывайте все системные свойства без разбора.

Проверка: тест проходит с defaults и с переопределёнными
`-D`; передача параметров подтверждена **внутри** тестовой JVM;
браузер закрыт и после успеха, и после контролируемого падения
(после проверки верните исходный assertion).

Ловушки AI: `-D` у launcher ≠ параметр в тестовой JVM;
`@BeforeAll` — на класс, а не «один раз на JVM».

### Фаза 2 — Ещё два теста

Цель: независимые детерминированные сценарии.

- Предложите два сценария и **проверьте их в реальном UI**
  до написания кода. Одного HTTP 200 недостаточно.
- Без привязки к числу результатов, порядку выдачи и
  изменяемым данным. Только ожидания Selenide, без `sleep`.
- Пример рабочей пары для обсуждения: позитивный поиск с
  переходом в конкретный репозиторий; empty state
  (`stars:<0` — только после проверки семантики запроса в UI).

Проверка: каждый тест отдельно и весь набор — с defaults
и в headless.

Ловушки AI: «огромное число stars» ≠ логически невозможное;
серия быстрых прогонов провоцирует GitHub HTTP 429 —
это внешний фактор, а не повод для ретраев.

### Фаза 3 — Page Object

Цель: читаемые сценарии, изолированные локаторы.

- Согласуйте стиль до реализации (не молча): fluent API,
  проверки в `should…`-методах страниц,
  `private final SelenideElement`-поля, имена методов —
  действия пользователя, компоненты — только при реальном
  повторении блоков.
- Минимум: `pages.SearchPage` (open/searchFor) и
  `pages.SearchResultsPage` (shouldHaveResult/shouldBeEmpty);
  тесты в package `tests`.
- Локаторы, assertions и порядок проверок — без изменений.

Проверка: все три теста зелёные, семантика идентична
коммиту до рефакторинга.

### Фаза 4 — Allure-отчёты

Цель: понятный отчёт с диагностикой падений.

- Разделите два слоя: **JVM-адаптеры** пишут результаты,
  **CLI-генератор** собирает HTML. Версии этих слоёв — разные,
  не путайте.
- Согласуйте версию генератора: Allure Report 3 (npm-пакет
  `allure` 3.x) или Report 2 CLI — это разные инструменты,
  обоснуйте выбор и зафиксируйте версию.
- Проверьте совместимость адаптера с вашей реальной версией
  JUnit (JUnit 6 ≠ JUnit 5 по имени артефакта!) и Selenide.
- Шаги: `@Step` (требует `-javaagent:aspectjweaver`)
  или `Allure.step` без агента — осознанный выбор.
- Вложения при падении: screenshot + page source
  (дефолты `AllureSelenide`).

Проверка: отчёт сгенерирован и открыт в браузере — 3 теста,
шаги видны; контролируемое падение показывает причину,
failed step и вложения; старые результаты не смешиваются
с новым прогоном (очистка `allure-results`); assertion
восстановлен, финальный прогон зелёный.

Ловушки AI: `allure-junit5` не публикуется для новых версий —
актуальный артефакт `allure-jupiter`; `@Step` без weaving
молча не работает; `allure generate`/`open` флаги проверяйте
по реальному `--help` вашей версии.

### Фаза 5 — GitHub Actions

Цель: воспроизводимый CI на hosted runner, без Selenoid.

До реализации согласуйте: события запуска, артефакты vs
опубликованный сайт, переопределяемые параметры.

- Явная подготовка: Java, браузер, драйвер, CLI отчёта.
  Не предполагайте, что нужный браузер уже установлен;
  сверяйте версию ChromeDriver с браузером и поддержкой CDP.
- Actions закрепляйте по SHA; `permissions` — минимальные;
  secrets коду fork PR не давать, `pull_request_target`
  для запуска кода не использовать.
- После падения сохраняйте JUnit XML, Allure results
  с вложениями и готовый отчёт — но job остаётся failure.
- Отделяйте ошибку компиляции от падения тестов;
  без результатов отчёт не генерируется («0 тестов» — не успех).

Проверка: реальный запуск в вашем GitHub — success;
контролируемое падение и ошибка сборки показывают
правильные статусы и нужные артефакты (временные ветки
удалите после проверки).

Ловушки AI: Chrome на hosted runner может требовать
`--no-sandbox` (принимайте компромисс осознанно, только для CI,
задокументируйте риск); dispatch-only workflow может не
индексироваться GitHub до первого push-триггера — проверяйте
фактическую регистрацию; Pages environment допускает
только заявленные ветки.

### Фаза 6 — Telegram-уведомления

Цель: информативное сообщение о результатах прогона.

Согласуйте до реализации: из каких CI уведомлять, для каких
исходов (success/failure/ошибка сборки/отмена), имена secrets,
поведение при их отсутствии и при ошибке API.

- Токен и chat ID — только из secrets/окружения; не хардкодить,
  не логировать (включая `-x`, verbose curl и тексты ошибок).
- Сообщение: проект, CI, branch/commit, статус,
  passed/failed/skipped, ссылка на запуск.
- Статистика — из JUnit XML (проверенный формат!), не из
  внутренних файлов Allure-отчёта. Учтите `failure`, `error`,
  `skipped` и несколько XML-файлов; не дублируйте вложенные
  `testsuite`.
- Отличайте «тесты не запускались/ошибка сборки» от
  «0 тестов прошло». Статус уведомления не должен маскировать
  исходный failure тестов.
- Проверяйте HTTP status и `ok` в ответе Telegram API,
  разумный timeout.

Проверка без реальной отправки (fixtures + mock HTTP):
success, failure, error, skipped, отсутствующий/битый XML,
ошибка до тестов, нет секретов, HTTP-ошибка, `ok=false`,
timeout; исходный failure сохраняется при ошибке уведомления.
Реальную отправку — только после согласования, затем сверьте
фактическое сообщение.

### Фаза 7 — Jenkins Pipeline

Цель: те же тесты и отчёт на Jenkins.

Уточните до реализации: расположение Jenkins и агента, ОС,
label, доступные Java/браузеры/CLI, параметры, имена
Credentials, способ публикации отчёта.

- `Jenkinsfile`: те же команды wrapper и генерации отчёта,
  что локально и в GitHub Actions; согласованные параметры;
  браузер на агенте без remote-инфраструктуры.
- Публикуйте JUnit XML; сохраняйте результаты, вложения
  и отчёт при падениях; не маскируйте падение статусом.
- Согласуйте различие FAILURE/UNSTABLE.
- Способ генерации отчёта: закреплённый CLI (как в CI)
  или доказанно совместимый Allure Jenkins plugin —
  не предполагайте совместимость заранее.
- Не устанавливайте плагины и не меняйте Jenkins глобально
  без разрешения. Не копируйте `--no-sandbox` как универсальную
  настройку — это компромисс конкретного runner.

Проверка на реальном агенте: успех, падение assertion,
ошибка компиляции, отсутствие результатов, сохранение
диагностики и уведомления. Если Jenkins недоступен —
проверен синтаксис Jenkinsfile, интеграция помечается
непроверенной.

## Анти-паттерны, за которые снижаем оценку

- «Агент написал — значит работает» без проверки.
- Падение тестов, «вылеченное» ретраями, `@Disabled` или
  `continue-on-error`.
- Секреты в коде, в логах или в чате с агентом.
- Коммиты `build/`, `allure-results`, `node_modules`,
  временной диагностики.
- Статус «выполнено» для конфигурации, ни разу не запущенной
  в реальном окружении.
- Смешение чужого WIP и своих изменений в одном коммите.
